# Adversarial critique of the Babble streaming video plan

## Which load-bearing claims are unverified or wrong?

### Takeaway
The prior report's spine — "H.264 depends on Flatpak codecs-extra, souphttpsrc range-seeking is reliable, GtkMediaFile over GVFS is impossible so download-then-play is proven, playbin3+gtk4paintablesink is ready in PyGObject, and Mastodon enforces 99 MB/1300 kbps" — is wrong or unproven on every leg. Direct inspection of the installed GNOME 51 Flatpak runtime inverts the codec story, the codebase's own instance-limit and GVFS evidence contradicts two more legs, and the two most load-bearing technical claims (range seeking, PyGObject sink readiness) were never tested.

### Cited Findings
- **H.264 decode does NOT live in `codecs-extra`; it ships in the GNOME 51 base runtime via `libgstlibav`, and `codecs-extra` is only the x264 *encoder*.** Verified on this machine against the installed `org.gnome.Platform//51` runtime: `flatpak run --command=sh org.gnome.Platform//51` shows `GST_PLUGIN_SYSTEM_PATH=...:/usr/lib/x86_64-linux-gnu/codecs-extra/lib/gstreamer-1.0:...` but `ls /usr/lib/x86_64-linux-gnu/codecs-extra/lib/gstreamer-1.0/` contains a single file, `libgstx264.so`, while `gst-inspect-1.0 avdec_h264` resolves to `/usr/lib/x86_64-linux-gnu/gstreamer-1.0/libgstlibav.so` (source module `gst-libav`), and `gst-inspect-1.0 gtk4paintablesink/playbin3/souphttpsrc/hlsdemux2` all resolve inside the base runtime. The prior report's claim that "H.264 MP4 remains the common case that depends on the extra branch" and that GNOME 51 gives "automatic H.264 support unless the user opted out" therefore misattributes the decoder. The maskable-extension risk is real for the encoder, not for playback decode. — [Local runtime inspection, `org.gnome.Platform//51` metadata + `gst-inspect-1.0` inside `flatpak run`]
- **VA-API and Vulkan decode are absent in the GNOME 51 runtime, contradicting the plan's "explicit pipeline choice / prefer VA-API or Vulkan" framing.** Same inspection: `gst-inspect-1.0 vaapih264dec` → NO, `gst-inspect-1.0 vulkanav1dec` → NO inside the runtime, and no `libgstvulkan`/`libgstvaapi` in the runtime plugin listing (host has `libgstvulkan.so` but the runtime does not expose the decoders). Hardware decode is not a deterministic choice Babble can make from inside the sandbox today; it is a missing-driver problem the plan treats as solved. The report's supporting citation for VA-API-on-Wayland is a single Arch forum post — [Arch forum report](https://bbs.archlinux.org/viewtopic.php?id=244031&p=12) — which the report itself labels "practitioner evidence rather than a guaranteed GTK backend default," then proceeds to design as if it were guaranteed.
- **`souphttpsrc` range seeking is not "overwhelmingly likely" to work; it sends `Range` unconditionally and fails hard when the server does not support it, and it fails on redirects.** GStreamer bug 722185 is titled "souphttpsrc: racy 'server does not support seeking'" and notes the element "adds range request headers regardless of whether the server supports range requests or not" and "aborts during playback" — [Bug 722185](https://bugzilla.gnome.org/show_bug.cgi?id=722185). The element docs state "If the server sends redirects, the request fails instead of following the redirect" — [souphttpsrc docs](https://gstreamer.freedesktop.org/documentation/soup/souphttpsrc.html). The prior report's counter is only that "object-storage defaults ... make progressive playback overwhelmingly likely" plus an unchecked `curl -I`. No `curl -I`, no `Accept-Ranges: bytes` evidence, no redirect check against `files.mastodon.social` or any S3-backed media host appears in the report or the notes. For a 99 MB H.264 file over a redirecting CDN, this is the entire feature, and it is assumed.
- **The "GVFS HTTP is unavailable inside Flatpak, therefore download-then-play" claim is a comment in Babble's own code, not a verified platform fact, and the report never tests the obvious alternative.** `src/mediaplayback.py:284-288` says "`Gtk.MediaFile` reads remote files through gvfs, whose http backend is unavailable inside a Flatpak sandbox (and hesitates with buffering hiccups on the host as well)," and `src/mediaplayback.py:320` only ever calls `Gtk.MediaFile.new_for_file(destination)` on a local temp file. No code path, test, or probe in the repo tries `Gtk.MediaFile`/`Gtk.Video` over an `https://` URI (`new_for_uri` / `Gio.File.new_for_uri`), which routes through GStreamer's `souphttpsrc`/`uridecodebin` rather than the GVFS HTTP backend. Tuba's benchmark proves the alternative is live in production: its GtkVideo fallback calls `video.set_file(File.new_for_uri(url))` directly for `stream=true` callers (audio-remote/Funkwhale/Drive/PeerTube), reserving download-then-play only for Mastodon video — `research_notes/Babble video adversarial Tuba review/tuba_benchmark.md`. The report repeats the codebase comment as established fact and builds the whole "progressive URI handoff" phase on it without a single `new_for_uri` experiment.
- **99 MB / 1300 kbps / 120 fps / one-video-per-post are defaults, not server guarantees, and Babble's own code says so.** The report states the limits as flat server behaviour. Babble already reads per-instance limits from `configuration.media_attachments` (`src/test-media-limits.py:67-76`, `src/mastodon.py` `media_size_limits()`), and the research notes record that "per-instance limits exposed at `configuration[media_attachments]`" vary, that "older instances still advertise 40 MB," and that mastodon.social showed "~68 MB observed despite 99 MB API value" — `research_notes/Babble streaming video implementation/mastodon_streaming_api.md`. Designing bandwidth, temp-disk, and data-saver budgets around a hardcoded 99 MB ceiling mis-sizes every instance that advertises less (or more).
- **The viewer download path has NO size cap, which the plan never mentions.** `imagecache` caps image responses at `MAX_IMAGE_RESPONSE_BYTES = 16 * 1024 * 1024` (`src/imagecache.py:71`), but `mediaplayback.download()` / `_Download` (`src/mediaplayback.py:51-176`) streams 64 KiB chunks to a temp file with no maximum at all. A 99 MB video therefore becomes a 99 MB temp file on every viewer open, with no eviction policy beyond viewer close. The plan's "reuse the existing viewer pipeline" phase inherits this unbounded disk write without flagging it as a defect streaming should fix.
- **`playbin3` + `gtk4paintablesink` "readiness in PyGObject" is asserted, never demonstrated.** The report cites the sink's DMABuf/GL caps from GStreamer docs — [gtk4paintablesink](https://gstreamer.freedesktop.org/documentation/gtk4/index.html) — but Babble contains zero `Gst.` usage anywhere (`grep -rn "Gst\." src/*.py` returns nothing), no `Gst.init()` call, no `Gst.parse_launch`, no bus handling, and no introspection test. `gtk4paintablesink` is a Rust plugin (`gst-plugin-gtk4`, MPL, from `gst-plugins-rs`), not a good/bad element, so its presence depends on the runtime shipping `libgstgtk4.so` — which it does today (verified above) but which the report never enumerates. Writing a pipeline in Python requires owning bus watches, `GST_EVENT_SELECT_STREAMS`, error/buffering messages, and thread marshaling, none of which the report scopes.
- **HLS absence is the one claim that holds — and it undermines the plan's own "adaptive insurance."** No `hls`/`m3u8`/`dash`/`adaptive` string exists in `src/` (verified by grep; only `mediaplayback.py`/`mediaviewer.py`/`mediabox.py` and upload/limit modules mention video), and Mastodon serves progressive files per [Mastodon posting docs](https://docs.joinmastodon.org/user/posting/). The report correctly concludes HLS is out of scope, then keeps `playbin3` justified partly as "adaptive insurance" and "any HLS-capable federated embeds." There is no federated HLS embed in Babble's data model (`status.card` is a link preview, not a player), so the insurance premium buys cover against a risk the codebase cannot express.
- **Flatpak `codecs-extra` auto-install/maskability is cited from freedesktop docs but never checked against GNOME 51's actual extension table.** The report cites [Flatpak extension docs](https://docs.flatpak.org/en/latest/extension.html) and [gnome-build-meta issue 931](https://gitlab.gnome.org/GNOME/gnome-build-meta/-/issues/931) for the `ffmpeg-full` → `codecs-extra` rename. The installed GNOME 51 metadata (above) shows `[Extension org.freedesktop.Platform.codecs-extra] version = 26.08-extra` with `autodelete = true` and no `no-autodownload`/`enable-if` gate — i.e. this runtime's extra branch is not even installed by default the way the report describes, and on this machine `26.08-extra` is present only because something else pulled it. The report's "practical expectation is automatic H.264 support" was never run through `flatpak info` or a sandbox `gst-inspect` before being written as a plan assumption.

### Inferences
- The codec phase of the plan (manifest amendment + `gst-inspect` probe + translated error naming the missing extension) is solving the wrong problem: decode is already in the base runtime, hardware decode is missing regardless of extensions, and the real silent failure is a server that does not do `Range` or that redirects. The probe list (`avdec_h264, vaapih264dec, souphttpsrc, playbin3, hlsdemux2, gtk4paintablesink`) would report `vaapih264dec=NO` on a clean GNOME 51 install and the plan has no answer for that besides "surface a translated error."
- Because `new_for_uri` was never tried, the entire "download-then-play is proven, now add progressive URI handoff" roadmap may be moot: if `Gtk.MediaFile.new_for_uri(https_url)` plays in the sandbox, Phase 1 collapses to "stop downloading in the viewer" — a smaller, higher-value change than building `mediainline.py`.

### Gaps
- No source in the report or notes enumerates the GNOME 51 runtime GStreamer plugin set from the manifest or from `flatpak run`; the direct inspection above is new and should be repeated on a clean machine (this host already has `codecs-extra` installed system-wide, which may mask a missing-default case).
- No `curl -I` / `Accept-Ranges` / redirect evidence for any Mastodon media host was found; cannot confirm or refute range support without network probing, which is exactly the experiment the plan defers.
- No PyGObject spike exists proving `gtk4paintablesink`'s `GdkPaintable` can be embedded in a `Gtk.Picture` from Python and survive `GSK_RENDERER=cairo`; the sink's DMABuf path requires GTK ≥ 4.14 with the `dmabuf` cargo feature enabled — [gtk4paintablesink docs](https://gstreamer.freedesktop.org/documentation/gtk4/index.html) — which the runtime build may or may not have.

## Is the two-tier split over-engineered or under-engineered?

### Takeaway
Both: over-engineered where it adds `playbin3`/track-selection/adaptive machinery Mastodon can never feed, and under-engineered where it assumes one active pipeline, one visibility rule, and one codec probe will tame a timeline of recycled rows each owning a GstPlay thread. The simpler winner the report dismisses — reuse `GtkVideo` everywhere and fix the viewer download path — is never costed.

### Cited Findings
- **Track selection / overlays / multi-track audio have no source data in Mastodon attachments.** The report justifies `playbin3` via `GstStreamCollection` and "advanced selection" — [playbin3 docs](https://gstreamer.freedesktop.org/documentation/playback/playbin3.html) — for "track selection, overlays, and adaptive insurance." But Mastodon transcodes video to single-track H.264 MP4 with AAC audio (see `meta.audio_encode`/`audio_bitrate` in the MediaAttachment entity — [MediaAttachment](https://docs.joinmastodon.org/entities/MediaAttachment/)), movies are one per post, and sidecar subtitles do not exist in the API. Tuba, which the report benchmarks against, ships no subtitle or track-selection UI at all in its viewer (benchmark notes). `playbin3`'s selection surface is capability with no caller.
- **`GtkVideo` already does what the timeline tier needs, and the viewer already proves it.** The report's own citation says `GtkVideo` "aims to cover use cases such as previews, embedded animations... supports autoplay, looping, and simple media controls" — [GtkVideo docs](https://docs.gtk.org/gtk4/class.Video.html) — and Babble's viewer already drives `Gtk.Video` + `Gtk.MediaFile` + `Gtk.MediaControls` for video (`src/mediaplayback.py:343-347`, `src/mediaplayback.py:391`), with `Gtk.Picture(paintable=stream)` for GIFV (`src/mediaplayback.py:327-330`). The report never explains why detail view needs a second engine when the first engine's detail player already ships, is tested (`src/test-mediaviewer-teardown.py`, 12 open/close cycles under `fatal_test_env` at `src/meson.build:395-399`), and handles autoplay/loop/mute. The Tuba benchmark shows the proven production shape is the same: Clapper preferred, `GtkVideo` fallback, download-then-play for Mastodon video, `set_file(uri)` for genuinely streamable sources.
- **The "one visible pipeline" cap plus per-row visibility gating is a second lifecycle system the report hand-waves.** The plan requires "at most one `GtkVideo` or `GtkMediaFile` at a time per viewport, muted and looping, started only when the row is at least half visible and no sibling pipeline is active, and torn down through pause, file release, and poster restoration on unmap, on scroll-away, or on focus theft." Babble has no `IntersectionObserver` — the report admits "GTK itself provides no IntersectionObserver and Babble must supply the visibility computation from layout bounds and scroll-container signals." Every timeline row is recycled by `Gtk.ListView`/`TimelineFactory` (`src/timelinepage.py` per `CLAUDE.md`), so the visibility coordinator must hook row bind/unbind, layout, and scroll signals with `connect_weak` discipline (`pages.connect_weak`, `CLAUDE.md`) across `mediabox.py`, `statusrow.py`, and `timelinebase.py` — on files that are already at their limits (below). A coordinator that plain-`connect`s a row to a global singleton creates the exact C-level cycle `test-timeline-memory.py` exists to catch.
- **External player and "improve the viewer download path" are dismissed in one table row each, without costing.** The alternatives table lists "External player launch: Zero codec burden but abandons inline playback, pause-offscreen discipline, and unified accessibility" and "WebKit and HTML video: ... weaker media-key and power semantics." But Babble already has a working external path: drag-out (`media_provider`, `src/mediaviewer.py:184-201`), "Open With…" downloading to cache and launching via `Gtk.FileLauncher` (`src/mediaviewer.py:882-919`), and "Open in Browser." For a 99 MB file the user explicitly opened, handing off to Totem/Showtime/Clapper is a legitimate degraded mode, and Tuba uses exactly this as its only external fallback (UNKNOWN type → download + `Host.open_url`). The report never considers "stream the viewer via `new_for_uri`, keep the timeline static, and let duration badges + GIFV animation be the only timeline change" — the Tuba benchmark's own recommendation ("inline muted-looping GIFV/video in the timeline with duration badges is the single highest-leverage feature") is narrower than the plan's two-tier build.
- **Duration badges and posters are server-supplied, so the `GstDiscoverer` fallback the plan prices in is unnecessary default work.** The report says "Discovery for duration badges and posters is a solved subproblem through `GstDiscoverer`," then admits "reusing server `preview_url` posters will remain cheaper." `meta` already carries duration, fps, size, dimensions, audio encoding and bitrate ([MediaAttachment](https://docs.joinmastodon.org/entities/MediaAttachment/)), `preview_url` is the poster, and `entities.attachment_still_url` already resolves the still (`src/entities.py:135-145`). Per-row probing would be pure overhead; the plan keeps it as a fallback branch that doubles test surface.

### Inferences
- The split survives only if detail view demonstrably outgrows `GtkVideo`. Today it doesn't: single-track, no captions, one video per post, `GtkMediaControls` already wired. `playbin3` should be gated behind "a Mastodon attachment with two selectable streams exists," which is falsifiable and currently false.
- The under-engineering is symmetrical: the plan budgets one pipeline but never budgets what happens on fast scroll (pipeline create/destroy churn), on window minimize/suspend (see below), or on network change mid-orbit. `release_media`'s ordering contract (`src/mediaplayback.py:186-209`, "never clear a MediaStream while the Gtk.Video that plays it may still be alive... SIGSEGV in `g_type_check_instance_is_fundamentally_a`") was written for one viewer; a timeline coordinator that creates/destroys GstPlay threads per row multiplies the race surface by the scroll rate, and the 12-cycle teardown test does not cover row recycling.

### Gaps
- No benchmark exists for `GtkVideo` instantiation cost in PyGObject on Wayland — the report admits this — so the "1 active pipeline" cap is a guess, not a measured threshold. The `PERFORMANCE.md`/`bench/timeline_bench.py` harness (Xvfb + Cairo, `main_ms`/`stall_max_ms`) could measure it but the plan doesn't schedule it.
- No estimate of `mediainline.py` size exists. Given the file-size constraints below, the coordinator + visibility + policy + error surface may not fit under 800 lines without a second module the roadmap doesn't name.

## What failure modes did the plan miss?

### Takeaway
At least nine failure modes — pipeline memory, hardware decode absence, codec masking vs. encoder confusion, live metered/power transitions, sensitive-media re-gating, reduced-motion gating for video (not just GIFV), notification/Catch-Up parity cost, signed-URL expiry mid-play, and app suspend/minimize — are unaddressed or addressed only as "check at construction time." Several are first-order: they will ship as silent black pictures, background audio, or leaked pipelines.

### Cited Findings
- **Multiple pipelines / RSS blowup.** Babble's memory budget is explicitly tight: `MEDIA_TEXTURE_CACHE_SIZE=48` decoded textures, `AVATAR_CACHE_SIZE=256`, viewer store of 6 kept separate "so opening a viewer would evict the timeline's thumbnails" (`src/mediaviewer.py:48-51`, `src/mediacache.py:371-376`), and `PERFORMANCE.md` records retained RSS near 96 MB after fixes. Each `Gtk.MediaFile`/`GtkVideo` owns a GstPlay pipeline with its own thread and decoder buffers — the teardown test exists because "the pipeline owns a signal-adapter thread" (`src/test-mediaviewer-teardown.py:5-10`). The plan caps pipeline count at one per viewport but never caps decoder DMABuf/SystemMemory allocation, never states a texture+pipeline combined budget, and never addresses fast-scroll create/destroy churn.
- **Wayland DMABuf/VA-API bugs are untestable in Babble's harness and absent in the runtime.** Tests pin `GSK_RENDERER=cairo` because "letting GSK pick a GL renderer makes the suite depend on a working GL context... libepoxy then aborts the process" (`src/meson.build:190-199`). `gtk4paintablesink`'s DMABuf path requires the `dmabuf` feature and GTK ≥ 4.14 — [gtk4paintablesink docs](https://gstreamer.freedesktop.org/documentation/gtk4/index.html) — and VA-API/Vulkan decoders are not in the GNOME 51 runtime (verified above). Under Cairo the sink falls back to system memory; under a real GPU it does not. The plan's "GPU-composited timeline playback without a system-memory bounce is available without heroic work" will be exercised by no test in the suite.
- **Flatpak codec masking: the report's threat model is the encoder, the real threat is the driver.** `org.freedesktop.Platform.GL.default` and `VAAPI.*` extensions are `enable-if = active-gl-driver` / `download-if = active-gl-driver` (GNOME 51 metadata), so hardware decode vanishes on hosts whose drivers don't match, regardless of `codecs-extra`. `--device=dri` is already in Babble's finish-args (`build-aux/flatpak/io.github.mauriciobc.Babble.json:15`), but DRI without VA-API driver extensions still leaves no `vaapih264dec`. The plan's "surface a translated in-app error naming the missing codec extension" would blame the wrong extension.
- **Metered / power-saver are checked once, at viewer construction, never while playing.** `MediaPlayback._show_stream` checks `_system_state('metered')` once (`src/mediaplayback.py:242-246`); GIFV autoplay checks `gtk-enable-animations` and power-saver once (`src/mediaplayback.py:341-342`); `sysstate.monitor()` emits `notify::metered`/`notify::power-saver` on change (`src/sysstate.py:92-100`) but no media code subscribes. A timeline that starts on Wi-Fi and moves to metered mid-scroll keeps decoding; power-saver engaged mid-GIFV keeps looping. `StreamingManager` already subscribes to `notify::online` (`src/streaming.py:196-198`) — media has no equivalent.
- **Sensitive media / CW gating is a grid-build check, not a playback check.** `MediaBox.set_media` applies the `show-sensitive-media` gate and the blurred revealer at build time (`src/mediabox.py:460-487`), `BlurredPicture` blurs at snapshot (`src/mediabox.py:412-424`), and `statusrow.py`/`catchup/rows.py`/`catchup/tiles_render.py` each re-read `show-spoilers`/`show-sensitive-media`. The plan says "the existing sensitive-media blur gate applied before any decode begins" but inline autoplay that instantiates a pipeline on visibility must re-check `media_revealed` on every reveal/hide toggle and on row recycle (`ui` dict persists across recycling, `src/mediabox.py:449-452`). A pipeline started while revealed keeps playing after the user hides the media.
- **Reduced-motion is gated for GIFV in the viewer but not for timeline video in the plan.** The viewer checks `Gtk.Settings.get_default().get_property('gtk-enable-animations')` for GIFV (`src/mediaplayback.py:341-342`) and `src/style.css` honours it for CSS animations. The plan's timeline tier autoplays *muted looping video* on visibility with no `gtk-enable-animations` gate — it only notes "No GNOME-wide reduced-motion mapping to autoplay was verified." Mastodon's own preference defaults autoplay-GIFs off for accessibility ([Mastodon preferences](https://docs.joinmastodon.org/user/preferences)), and `Section508` guidance warns autoplaying content "can interfere with assistive technologies" — [Section508 blog](https://www.section508.gov/blog/avoid-auto-playing-content/). Shipping video autoplay where GIFV autoplay is gated is a regression against Babble's own policy.
- **Notification and Catch-Up parity is not a Phase 2 checkbox; both surfaces currently have no media open path at all.** `notificationrow.py` renders static 96px thumbnails with no click-to-viewer (`src/notificationrow.py:296-320`), and Catch-Up tiles show a play icon but "click opens thread not playback" (`src/catchup/tiles_render.py:410-434`, tile click → `push_thread`). The plan lists `notificationrow.py` + `catchup/tiles_render.py` as "parity" changes without noting that parity requires inventing the click handling, keyboard handling, and sensitive gating those surfaces lack — each is a new feature, not a sync.
- **Signed / expiring URLs and `url: null` transcoding state break streaming differently than downloading.** `mediaviewer.show_index` trusts `attachment.get('url') or attachment.get('remote_url')` with "no re-fetch, no signature, no expiry check" (`src/mediaviewer.py:606`). A downloaded file is immune to expiry after fetch; a streamed URI is not — mid-play 403/expiry has no recovery path (no refresh via `GET /api/v1/media/:id`, no fallback to download). The plan waves this off as "should not block the progressive MVP" but streaming is strictly worse here than the status quo. `url: null` + `preview_url` present (own-upload transcoding, `src/api/media.py` polling) also means the timeline tile must distinguish "no URL yet" from "no video" for the play affordance.
- **App lifecycle / suspend / minimize: the viewer inhibits idle; the timeline explicitly does not; neither pauses on background.** `MediaPlayback._on_stream_playing` inhibits idle only for `video`/`audio`, never for muted looping GIFV ("A muted, looping GIFV is no reason to keep the screen on," `src/mediaplayback.py:417-420`), and `_set_inhibited` uninhibits on every stop path (`src/mediaplayback.py:427-447`). The plan's timeline tier ("never survives window minimisation or sleep as a background track") has no mechanism: no `notify::fullscreened`/window-state handler, no `Gtk.Application` shutdown pause, no `sysstate` `notify::online` pause, no audio-session handling. GstPlay pipelines keep their threads alive when paused ("a paused GstPlay still has its adapter thread," `src/mediaplayback.py:199-201`), so suspend with a paused-but-live pipeline is the default outcome.
- **Audio focus / MPRIS is dismissed with anecdotes, not a Flatpak permission analysis.** The report cites Celluloid/Totem MPRIS bugs — [Celluloid issue #452](https://github.com/celluloid-player/celluloid/issues/452), [KDE bugzilla](https://bugs.kde.org/show_bug.cgi?id=456516) — and declares MPRIS out of scope. Babble's manifest has no `--own-name=org.mpris.MediaPlayer2.*` (contrast Tuba's `--own-name=org.mpris.MediaPlayer2.Tuba.*` in the benchmark), so any future decision needs a manifest change the plan never lists. Meanwhile timeline video that is muted by construction still decodes audio tracks it never plays.

### Inferences
- The most dangerous missed mode is the combination: software-decode fallback (no VA-API) + muted looping autoplay + no reduced-motion gate + no metered re-check = battery drain and data use on every scroll, with no test able to observe it under Cairo.
- Sensitive-media handling will leak if visibility triggers pipeline creation independently of the `media_revealed` UI state; the blur gate is on the poster, not on the stream.

### Gaps
- No brain on whether `gtk4paintablesink` under `GSK_RENDERER=cairo` works at all (system-memory path) vs. requiring GL — untested, and the suite cannot test the GL path by construction.
- No measurement of per-pipeline RSS/CPU in PyGObject on Wayland; the "one pipeline" cap is unvalidated against the 96 MB retained-RSS budget.
- Whether Mastodon media hosts issue signed URLs at all is undocumented ("I found no reliable source confirming signed media URLs" — research notes); the failure mode is therefore unscoped, not absent.

## Where does the plan violate Babble's own constraints?

### Takeaway
The roadmap as written cannot land: four of the files it names for direct extension are within 20 lines of the 800-line limit (two are exceptions or near-exceptions that the file-size rule will reject without a declared split), the new module needs three registries the plan mentions only in passing, and the test strategy contradicts the harness pins it claims to respect.

### Cited Findings
- **File-size rule: `statusrow.py` (793), `notificationrow.py` (797), `catchup/tiles_render.py` (785) are 7, 3, and 15 lines under the limit.** Measured: `src/statusrow.py` 793 lines, `src/mediabox.py` 667, `src/notificationrow.py` 797, `src/catchup/tiles_render.py` 785. `src/test-file-size.py:35` sets `LIMIT = 800` and fails on any module over the limit that is "in neither SEAMS nor EXCEPTIONS" (`src/test-file-size.py:138-142`). `mediaviewer.py` (1058 lines) is a declared exception (`src/test-file-size.py:72-76`); `statusrow.py`, `notificationrow.py`, and `tiles_render.py` are not listed as exceptions and have no declared reason. The plan's Phase 1 ("extends `mediabox.py` and `statusrow.py` with lazy cell construction"), Phase 2 ("notification and Catch-Up parity in `notificationrow.py` and `catchup/tiles_render.py`"), and the one-pipeline coordinator all add code to files with single-digit headroom. `mediabox.py` at 667 lines has room for a badge, not for visibility computation plus coordinator wiring.
- **Weak-signal discipline is load-bearing and the plan's coordinator is exactly the construct that breaks it.** `CLAUDE.md` requires `pages.connect_weak(emitter, signal, self.method)` or `pages.weak_method(...)` because "a plain connect forms a C-level cycle that Python's GC cannot see, and the row, page, or dialog leaks," pinned by `test-timeline-memory.py`. A module-level visibility coordinator that rows connect to with plain `connect` keeps every row alive — the plan mentions `connect_weak` once in passing ("every per-row observer must use `pages.connect_weak`") but the coordinator itself (a process-wide singleton like `sysstate.monitor()`) is the lifetime trap `sysstate.py:16-17` already warns about ("Consumers connect with `pages.connect_weak`: the monitor lives for the whole process and must not keep a page or a window alive").
- **Geometry harness: inline video changes row geometry, and the two geometry tests are the ones that will flake.** `compose widgets` and `timeline memory` "assert window geometry" and fail at any virtual-monitor size other than 1280x1024 (`AGENTS.md`). `MediaBox` tiles have fixed heights (`src/mediabox.py:491-496`: 260/160/130 px by count) with `Gtk.Picture` sized by texture; swapping a `GtkPicture` for a `GtkVideo` whose intrinsic size comes from the stream (`GtkMediaFile.get_intrinsic_width/height`) changes measurement. The plan's "extend the geometry-sensitive pair to assert that inline video preserves row geometry at 1280x1024" acknowledges the risk but the test env pins `LANG=C`/`GSK_RENDERER=cairo` (`src/meson.build:225-227`), under which the video widget cannot render — the test can assert geometry of a widget that paints nothing.
- **Teardown SIGSEGV multiplies.** `release_media`'s contract exists because "freeing the stream while the widget is still alive frees what the thread is using... SIGSEGV in `g_type_check_instance_is_fundamentally_a`" (`src/mediaplayback.py:186-201`, `CLAUDE.md`), pinned by 12 cycles in `src/test-mediaviewer-teardown.py:190`. The plan's per-row coordinator must replicate this ordering on every recycle, not just viewer close, and the teardown test's Theora clip (`src/test-mediaviewer-teardown.py:89-174`) deliberately avoids H.264 because "an H.264 clip also needs a decoder that GTK does not [ship]" (`src/test-mediaviewer-teardown.py:86-88`). A timeline test with a real H.264 clip cannot run in CI without the codec the plan is still probing for.
- **Install/POTFILES registries: the plan names `src/meson.build` once but the rule checks three lists.** `test-file-size.py` fails when a module is "not in `src/meson.build` install_data" (`src/test-file-size.py:152-160`), when a translating module is "not in `po/POTFILES.in`" (`src/test-file-size.py:196-209`), and enforces `module boundary` import restrictions (`CLAUDE.md`). A new `mediainline.py` that translates strings (autoplay toggles, error names for the missing codec) must land in both `install_data` and `POTFILES.in`, and any Catch-Up-adjacent helper must respect the rank-module import boundary. The roadmap's Phase 1 file list omits `po/POTFILES.in` and the boundary test entirely.
- **`mediaviewer.py` is already an 1058-line declared exception; growing it is the known failure mode.** `src/test-file-size.py:72-76` records that ARCH-14 and ARCH-19 already extracted `mediaplayback.py` and `mediazoom.py` out of it. The plan's "refactors `mediaplayback.py` to expose progressive URI handoff" plus "Phase two expands detail view through upgraded `mediaviewer.py` chrome" pushes both files toward the limit without naming the next split. `mediaplayback.py` is at 459 lines — the URI-handoff + inline policy + coordinator will not fit in the remaining ~340 lines if it also owns error mapping and capability probing.

### Inferences
- The plan's Phase 1 as tabled is unimplementable without first splitting `statusrow.py`/`notificationrow.py`/`tiles_render.py` or declaring new exceptions with recorded reasons — which is itself a reviewable decision the plan should surface, not discover at PR time via `file size rule` failure.
- The test strategy ("embed a base-plugin Theora clip for network-free decode verification") proves decode, not streaming: it cannot verify `Range` seeking, redirect handling, codec-extension presence, DMABuf rendering, or the one-pipeline cap, which are the features being built.

### Gaps
- No line budget per file is given in the plan; cannot confirm `mediainline.py` fits under 800 lines with coordinator + visibility + policy + errors + probing.
- Whether `test-timeline-memory.py`'s geometry assertions survive a `GtkVideo` intrinsic size under Cairo is unknown and untested.

## What experiments must precede any code, and what would change the recommendation if they fail?

### Takeaway
Six cheap, decisive experiments — none requiring product code — would falsify or confirm every load-bearing assumption. If `new_for_uri` plays in the sandbox, or range-seeking fails on real media hosts, or the coordinator cannot stay under the file-size rule, the two-tier plan collapses to a smaller change. Run these before writing `mediainline.py`.

### Cited Findings
- **Experiment 1 — `Gtk.MediaFile.new_for_uri` in the Flatpak sandbox (falsifies the GVFS/download premise).** In a `flatpak run` of Babble (or a minimal `Gtk.Video` spike), play `https://files.mastodon.social/...mp4` via `Gtk.MediaFile.new_for_uri` / `Gtk.Video.new_for_uri` and via `Gio.File.new_for_uri` + `new_for_file`. Record which path plays, which errors, and whether the error is GVFS-related or codec-related. Tuba's `stream=true` path (`set_file(File.new_for_uri(url))`) predicts URI playback works for at least some callers. If URI playback works, Phase 1's "progressive URI handoff beside the existing full-download path" becomes "delete the download" — a different, smaller plan.
- **Experiment 2 — Range/redirect probe against real media hosts (falsifies souphttpsrc seeking).** `curl -I` (and `curl -r 0-1023`) against live `url` values from `mastodon.social` and at least one small-instance S3 host; record `Accept-Ranges`, `Content-Range`, 206 vs 200, and `Location` redirects. Then play the same URL through `souphttpsrc`/`playbin3` in the sandbox and seek to 50%. If the host returns 200 to a Range request or redirects, `souphttpsrc` will fail per [Bug 722185](https://bugzilla.gnome.org/show_bug.cgi?id=722185) and the fallback is download-then-play or a proxy — not inline streaming.
- **Experiment 3 — GNOME 51 runtime plugin inventory on a clean machine (falsifies the codec narrative).** On a host without pre-installed `codecs-extra`, run the `flatpak run --command=sh org.gnome.Platform//51` `gst-inspect-1.0` matrix from this critique (`avdec_h264`, `vaapih264dec`, `souphttpsrc`, `playbin3`, `hlsdemux2`, `gtk4paintablesink`, `vulkanav1dec`) and `ls` the `codecs-extra` plugin dir. This critique found `libgstlibav` (decode) in base and only `libgstx264` (encoder) in extra, with VA-API/Vulkan absent. If a clean install confirms it, the manifest amendment is deleted from the roadmap and hardware decode is recorded as unavailable, changing the performance story entirely.
- **Experiment 4 — `gtk4paintablesink` in PyGObject under Cairo and under GL (falsifies sink readiness).** Spike `Gst.init()`, build `playbin3 ! gtk4paintablesink`, call `get_paintable()`, embed in `Gtk.Picture`, play the Theora clip and a real H.264 clip, under `GSK_RENDERER=cairo` (CI env) and default GL. Record whether the paintable renders, whether bus errors surface as Python exceptions or criticals (fatal under `G_DEBUG=fatal-criticals`), and who owns the pipeline thread on widget disposal. If Cairo cannot render the sink, the test suite cannot cover Phase 2 and the playbin3 tier must be manual-test-only — a strong argument for staying on `GtkVideo`.
- **Experiment 5 — Per-pipeline cost on Wayland (sizes the "one pipeline" cap).** Under headless mutter (`mutter --headless --wayland --virtual-monitor 1280x1024`, per `AGENTS.md`), instantiate 1, 2, and 4 `GtkVideo` pipelines in PyGObject, play a 1300 kbps clip, and measure RSS/CPU via the existing `bench/timeline_bench.py` harness (`main_ms`, `stall_max_ms`). If one pipeline costs more than the retained-RSS budget allows on fast scroll (create/destroy churn), the timeline tier is infeasible without a shared pipeline, which `GtkVideo` does not support — and the plan must be re-scoped to GIFV-only animation.
- **Experiment 6 — File-size / registry dry run (falsifies roadmap implementability).** Sketch `mediainline.py` (coordinator + visibility + policy + errors + probe) on paper against `src/test-file-size.py` limits: which files grow, by how much, which split is needed, and whether the new module needs `po/POTFILES.in` + `module boundary` review. If `statusrow.py`/`notificationrow.py`/`tiles_render.py` must split before inline video can land, that split is Phase 0 and should be costed as such.

### Inferences
- Experiments 1 and 2 are the kill criteria: if URI playback works and Range works, the plan's hardest problems (download UX, temp disk, codec probing) shrink to "use the URI path"; if either fails, inline streaming is not shippable and the correct recommendation is "improve the viewer (cache, cap, progress) + GIFV timeline animation + duration badges," which is what Tuba's benchmark already recommends as the highest-leverage slice.
- Experiment 4 is the playbin3 gate: without a Cairo-renderable Python sink, Phase 2 cannot be CI-tested in Babble's harness and should be cut.

### Gaps
- None of these experiments appear in the prior report's "What remains uncertain" section as scheduled work; the report lists the unknowns but sequences widget work first in its roadmap table. The ordering is the finding.
