# Stream progressive video inside Babble timelines

Babble should ship inline progressive playback of Mastodon attachments, not HLS adaptive streaming, because Mastodon serves video as **progressive H.264 MP4 files** with no HLS endpoint and Babble today only plays video after fully downloading it inside a full-screen viewer. The significance is that “streaming video” for Babble means solving **incremental play from a remote HTTP range source** rather than implementing a manifest ladder, which redirects the entire design toward a two-tier GTK widget over GStreamer instead of a new protocol stack. The impact is a phased rollout that reuses Babble’s existing viewer pipeline, adds one active timeline pipeline at a time, and gates every launch behind the Flatpak codec story and the headless-mutter test harness. The essential context is that `Gtk.Video` with `Gtk.MediaFile` covers timeline previews and a simple detail player, while a direct `playbin3` plus `gtk4paintablesink` path is the only route to track selection, overlays, and adaptive insurance, and both paths must respect sensitive-media, autoplay, and metered-connection policies that Babble already enforces in the viewer.

## Mastodon serves progressive files, never adaptive playlists

Mastodon treats `video` as a sound clip and `gifv` as a looping soundless animation, both delivered through MediaAttachment `url` as **the original full-size location** and `preview_url` as the scaled-down poster, with `remote_url` reserved for the remote original and often null for local media. The server transcodes user uploads into that shape rather than generating a ladder: **videos (MP4, M4V, MOV, WebM) are limited to 99 MB and transcoded to H.264 MP4 at a maximum of 1300 kbps and 120 fps, with only one video per post**, while **soundless MP4 and WebM GIF uploads are converted to soundless MP4s so clients loop them like animated GIFs** ([Source](https://docs.joinmastodon.org/user/posting/)). The `meta` hash reinforces that progressive model by carrying duration, fps, size, dimensions, audio encoding and bitrate, plus `small` and `original` subtrees, which is exactly the metadata a client needs for aspect-correct posters and duration badges without probing the file ([Source](https://docs.joinmastodon.org/entities/MediaAttachment/)). Focal-point coordinates in `meta[focus]` and a nullable `blurhash` provide smart cropping and a colorful pre-download placeholder, which makes the thumbnail-first design cheap because the server already produced both artefacts ([Source](https://docs.joinmastodon.org/entities/MediaAttachment/)).

The WebSocket “streaming API” in Mastodon is a completely different channel for real-time timeline and notification delivery, subscribing to server-sent events over a long-lived connection multiplexed through control messages or single-stream query parameters on `wss://` hosts that may differ from the REST host. That endpoint also requires a user token with `read` scope, and media itself arrives through ordinary HTTPS GETs against the REST `url` on object-storage hosts such as `files.mastodon.social`, which confirms that timeline push and media playback share no machinery with video delivery ([Source](https://docs.joinmastodon.org/methods/streaming/)). PeerTube is the Fediverse exception that performs actual HLS VOD playback through playlists and segment fetchers, but no equivalent `m3u8` endpoint exists for Mastodon attachments, so any Babble HLS work would be building infrastructure the server does not expose ([Source](https://docs.joinpeertube.org/contribute/architecture)). The correct mental model for Babble is therefore **thumbnail plus blurhash now, progressive MP4 with HTTP range seeking on explicit play**, with adaptive demuxers retained only as free insurance in the pipeline rather than as a user-facing feature, because new `*demux2` adaptive elements are the current client-side implementation for HLS, DASH, and Smooth Streaming yet Mastodon never hands the client a manifest to demux ([Source](https://gstreamer.freedesktop.org/documentation/additional/design/adaptive-demuxer.html)).

Security and bandwidth follow from the same model: the client should load local `url` rather than `remote_url`, because the local instance already caches remote media on its files host, and it should never attach the OAuth bearer token to media GETs since anonymous access is the design and leaking the token to CDNs or origin servers would broaden the privacy leak beyond the instance proxy boundary ([Source](https://docs.joinmastodon.org/entities/MediaAttachment/)). Remote caching with multi-week retention is server behaviour that Babble inherits for free, which means Babble does not need its own media proxy; it needs to avoid defeating the proxy by fetching origin URLs directly ([Source](https://masto.host/re-mastodon-media-storage)). Sensitive-media handling is already specified upstream through blurred click-through overlays and an autoplay-GIF default that is disabled for accessibility, and Babble mirrors those preferences through `show-sensitive-media` and `show-spoilers` flags plus metered and power-saver gating, so inline playback must check those gates before a pipeline is even constructed ([Source](https://docs.joinmastodon.org/user/preferences)).

## Babble today downloads whole videos for a viewer-only room

Babble’s media path is thumbnail-first inside timelines and viewer-only for playback, because `entities.attachment_still_url` resolves `image` to `url` or `preview_url` and everything else to `preview_url` or `url`, and every timeline tile in `mediabox.MediaBox` draws a static `Gtk.Picture` texture from `_TextureCache` with at most four visual attachments per post, a play glyph for `video`, and a GIF badge for `gifv` (`src/mediabox.py`, `src/entities.py`). The cache underneath is a bounded LRU of 48 decoded textures with coalesced in-flight fetches, a 30-second soup session timeout, and decode budgets of 16 megapixels and 8192 pixels executed in worker threads, which is a poster pipeline rather than a streaming pipeline (`src/mediacache.py`, `src/timelinebase.py`). Notification rows and Catch-Up tiles reuse the same static-texture approach, and the composer limits video and audio to a lone attachment with first-frame or icon thumbnails, so the user-facing truth is that **no timeline surface currently realizes a `Gtk.MediaFile`** and even a click in Catch-Up opens the thread instead of playing media (`src/notificationrow.py`, `src/catchup/tiles_render.py`, `src/composeattach.py`).

The full-screen experience in `MediaViewer` classifies by attachment type and sends `video`, `gifv`, and `audio` into `mediaplayback._show_stream`, which downloads **the entire file through libsoup in 64 KiB chunks to an atomic temporary file** because `Gtk.MediaFile` over GVFS HTTP is unavailable inside the Flatpak sandbox, and only then starts `Gtk.MediaFile.new_for_file` with `Gtk.Video` for video, a muted looping `Gtk.Picture` for GIFV, and `Gtk.MediaControls` for audio (`src/mediaviewer.py`, `src/mediaplayback.py`). Metered connections already defer that download behind a preview and a Load button, power-saver blocks GIFV autoplay, and the 6-entry viewer texture store is deliberately separate from the 48-entry timeline cache so full-screen inspection cannot evict scrolling posters. The teardown contract is equally instructive: `release_media` must pause, drop the widget, and let widget disposal retire the GstPlay thread because clearing the stream or nulling it while the widget lives triggers a documented SIGSEGV in `g_type_check_instance_is_fundamentally_a`, a rule pinned by 12 open-close cycles in the teardown test (`src/mediaplayback.py`, `src/test-mediaviewer-teardown.py`). Repository-wide search confirms the gap from the other direction: references to `Gtk.Video`, `Gtk.MediaFile`, GstPlay, HLS, `m3u8`, MP4, and WebM cluster only in `mediaplayback.py`, `mediaviewer.py`, `mediabox.py`, and the upload and size-limit modules, while `streaming.py` is the WebSocket timeline manager rather than any form of video streaming.

That architecture leaves three concrete gaps for the product. Inline playback is entirely greenfield because there is no per-row video lifecycle, no progress or seek outside viewer `Gtk.MediaControls`, and no visibility-driven pause policy. Adaptive support is entirely absent because there is no `hls`, `dash`, or `adaptive` handling anywhere and the Flatpak manifest declares no `gst-plugins-bad` or HLS demuxer that adaptive playback would require. URL handling trusts `url`, `preview_url`, and `remote_url` directly, with no re-fetch, signature refresh, or proxy rewrite, so any future presigned-URL expiry would break media once and leave no recovery path (`src/mediaviewer.py`, `src/imagecache.py`).

## GtkVideo wins the timeline while playbin3 owns detail playback

The technology decision splits cleanly by surface. `Gtk.Video` is explicitly scoped to previews and embedded animations with `autoplay`, `loop`, and simple controls, and its documentation directs authors of full players toward `GdkPaintable` with a media framework such as GStreamer instead, making it the right primitive for a muted looping timeline cell and the wrong primitive for a detail player with overlays, multichannel audio, or device selection ([Source](https://docs.gtk.org/gtk4/class.Video.html)). `Gtk.MediaFile` supplies the stream abstraction underneath it, including duration, ended, error, has-audio, has-video, loop, muted, playing, prepared, seekable, seeking, timestamp, and volume state, which is sufficient for play, pause, and seek but intentionally lacks track selection, captions, and adaptive-variant control ([Source](https://docs.gtk.org/gtk4/class.MediaFile.html)). The direct GStreamer route fills exactly that gap through `playbin3`, which simplifies audio, video, and subtitle stream selection and publishes a `GstStreamCollection` for advanced selection, a capability legacy `playbin` cannot reach because new `adaptivedemux2` elements require streams-aware players such as `playbin3` and `uridecodebin3` ([Source](https://gstreamer.freedesktop.org/documentation/playback/playbin3.html)).

Display on Wayland is settled by `gtk4paintablesink`, the GTK4 video sink that exposes a `GdkPaintable` and can emit GL textures or, with GTK 4.14 or newer, DMABufs directly when built with the appropriate features, with pad caps covering DMABuf, GLMemory, and system-memory raw formats ([Source](https://gstreamer.freedesktop.org/documentation/gtk4/index.html)). That sink is the critical difference from `GtkVideo`, whose default pipeline cannot be customized, and its `reconfigure-on-window-resize` default of overlay-only keeps timeline re-sizes cheap without re-dimensioning upstream decoders. Hardware acceleration then becomes an explicit pipeline choice rather than a GTK backend accident: GStreamer spans VA-API, V4L2, NVIDIA NVCODEC, Intel QSV, Vulkan, DMA-BUF, KMS and DRM, and Wayland, with clocking for audio-video synchronisation and quality-of-service shedding under CPU pressure, and Vulkan video extensions now cover H.264 and H.265 decode on current drivers ([Source](https://gstreamer.freedesktop.org/features/)) ([Source](https://www.khronos.org/blog/khronos-finalizes-vulkan-video-extensions-for-accelerated-h.264-and-h.265-decode)). Container and codec coverage for the progressive workload is already present in the GStreamer feature set, including MP4, fragmented MP4, Matroska and WebM, HLS, DASH, HTTP, and the H.264, H.265, VP8, VP9, AV1, Opus, and AAC families reached through hardware decoders or FFmpeg ([Source](https://gstreamer.freedesktop.org/features/)). Discovery for duration badges and posters is a solved subproblem through `GstDiscoverer` in `pbutils`, which probes duration, streams, and bitrates and is available from Python via `Gst.init()` and `GstPbutils`, though reusing server `preview_url` posters will remain cheaper than rasterizing frames per timeline row ([Source](https://gstreamer.freedesktop.org/documentation/pbutils/gstdiscoverer.html)) ([Source](https://api.pygobject.gnome.org/Gst-1.0/index.html)).

| Playback option | Why it fits or fails in Babble |
|---|---|
| `Gtk.Video` plus `Gtk.MediaFile` | Smallest delta from current viewer; native autoplay, loop, and `Gtk.MediaControls`; insufficient for track selection and overlays |
| `playbin3` plus `gtk4paintablesink` | Full pipeline control, adaptive insurance, DMABuf and VA-API selection; more PyGObject surface and pipeline lifecycle to own |
| Clapper and ClapperGtk | GStreamer-backed GTK4 player with GObject Introspection bindings under LGPL-2.1-or-later, but unstable pre-1.0 and absent from `org.gnome.Platform`, so vendoring cost applies ([Source](https://github.com/Rafostar/clapper)) |
| libVLC and libmpv embedding | Contemporary failures to behave inside GTK4 windows and GTK3-only Celluloid lineage make either a poor drop-in for a GTK 4.24 app ([Source](https://stackoverflow.com/questions/56045346/python-vlc-will-not-embed-gtk-widget-into-window-but-open-a-new-window-instead)) ([Source](https://celluloid-player.github.io/)) |
| External player launch | Zero codec burden but abandons inline playback, pause-offscreen discipline, and unified accessibility |
| WebKit and HTML video | Browser codecs without pipeline control and with weaker media-key and power semantics |

The alternatives fail for structural rather than aesthetic reasons. Clapper is genuinely GNOME-native and GObject-Introspectable, yet its own readme warns that both libraries should be considered unstable until version 1.0 and nothing in `org.gnome.Platform` ships them, so adoption means adding a dependency and owning its API churn ([Source](https://github.com/Rafostar/clapper)). Celluloid interacts with mpv through libmpv but remains a GTK3 frontend rather than a GTK4 module, and community experience shows libVLC opening a separate unmanaged window instead of embedding when asked to play inside a GTK widget ([Source](https://codeberg.org/celluloid-player/celluloid)) ([Source](https://celluloid-player.github.io/)). GStreamer itself remains LGPL with a stable 1.x ABI, which preserves the option of writing a Rust or C helper later if PyGObject ever becomes a hot-path bottleneck, without paying that cost for the initial progressive feature ([Source](https://gstreamer.freedesktop.org/features/)). The recommended split is therefore deliberately hybrid: keep `GtkVideo` for the one visible timeline cell and the GIFV loop, keep the existing viewer working on `GtkMediaFile` for its first milestone, and isolate the single future browser-grade player behind a `playbin3` plus `gtk4paintablesink` module that only detail view and any HLS-capable federated embeds will touch.

Accessibility and power policy are where the two paths diverge most consequentially. `GtkVideo` already implements `GtkAccessible` and delegates playback chrome to `GtkMediaControls`, so keyboard focus, accessible names, and announcement plumbing arrive without bespoke widgets, whereas a custom sink demands that Babble reimplement the same affordances around the paintable ([Source](https://docs.gtk.org/gtk4/class.Video.html)) ([Source](https://lazka.github.io/pgi-docs/Gtk-4.0/classes/MediaControls.html)). Autoplay itself is the sensitive surface: autoplaying content can interfere with assistive technologies and distract users, which is why muted autoplay with a visible keyboard-toggleable pause control is the accessible pattern, and HTML runtimes express it as muted, looping, `playsinline` playback rather than an unmuted stream claiming audio focus ([Source](https://www.section508.gov/blog/avoid-auto-playing-content/)) ([Source](https://thoughtbot.com/blog/can-auto-playing-videos-be-accessible)). MPRIS media keys and lockscreen integration should stay out of scope because even dedicated players carry detection bugs there, with Celluloid reporting that the GNOME media applet cannot detect it and Totem’s interface described as only play and pause without metadata, which are poor precedents to copy into a timeline client ([Source](https://github.com/celluloid-player/celluloid/issues/452)) ([Source](https://bugs.kde.org/show_bug.cgi?id=456516)). Timeline playback should therefore never grab audio focus, never keep decoding off-screen, and never survive window minimisation or sleep as a background track.

## Flatpak codecs and hardware decide what actually plays

The Flatpak codec story is the largest silent-failure risk because GStreamer’s playback graph is only as complete as the runtime and extensions installed beside the app, and Babble’s current `org.gnome.Platform 51` manifest declares network, IPC, Wayland, DRI, and secrets finish-args plus `libspelling` and `libpeas` modules without any GStreamer plugin add-on, codec extension, or FFmpeg bundle (`build-aux/flatpak/io.github.mauriciobc.Babble.json`). Freedesktop-based runtimes supply patented-codec access through two different extensions whose meaning changed across release trains: `org.freedesktop.Platform.ffmpeg-full` must be explicitly added through `add-extensions` with a branch matching the base runtime, while its successor `org.freedesktop.Platform.codecs-extra` for 25.08-era branches is installed automatically by the runtime and can be masked by the user, and the older `openh264` fallback has been discontinued since the 25.08 SDK ([Source](https://docs.flatpak.org/en/latest/extension.html)). GNOME-build-meta documentation confirms the rename and the intentional user-maskability of the extra branch, so on GNOME 51 the practical expectation is automatic H.264 support unless the user opted out, with the explicit manifest amendment retained as insurance for older base runtimes ([Source](https://gitlab.gnome.org/GNOME/gnome-build-meta/-/issues/931)). WebM, VP9, and Opus do not share that risk because they are patent-free and flow through the base runtime’s `libvpx` and Opus plugins, which makes GIFV WebM uploads the resilient baseline while H.264 MP4 remains the common case that depends on the extra branch.

Hardware path selection follows the same logic. `gtk4paintablesink` supports DMABuf rendering directly on Linux from GTK 4.14 onward, and Babble targets GTK 4.24, so GPU-composited timeline playback without a system-memory bounce is available without heroic work ([Source](https://gstreamer.freedesktop.org/documentation/gtk4/index.html)). VA-API hardware decode on Wayland is reported working for Intel GPUs in the community and Epiphany already relies on GStreamer hardware paths on Wayland, but that is practitioner evidence rather than a guaranteed GTK backend default, which is precisely why the custom sink path matters: it lets Babble prefer VA-API or Vulkan elements deterministically instead of inheriting whatever `GtkMediaFile` selects ([Source](https://bbs.archlinux.org/viewtopic.php?id=244031&p=12)). Clapper’s Flatpak practice of bundling all required codecs and patches is the instructive contrast, signalling that distributors concerned with first-run codec success treat codec bundling as a product decision rather than a background detail ([Source](https://github.com/Rafostar/clapper)). Babble should therefore probe the runtime at development time with `gst-inspect-1.0`, record the presence of `avdec_h264`, `vaapih264dec`, `souphttpsrc`, `playbin3`, `hlsdemux2`, and `gtk4paintablesink`, and surface a translated in-app error naming the missing codec extension rather than a silent black picture.

## A two-tier widget plus staged rollout fits the harness

The widget design should be a two-tier system rather than a universal player, because Mastodon permits only one video per post while allowing four images, which means carousels belong to images and detail navigation, not to video lists ([Source](https://docs.joinmastodon.org/user/posting/)). The unfocused timeline cell needs only a `GtkPicture` from server `preview_url`, a centered play button labelled with the author and video, and a duration badge drawn from attachment `meta`, with zero realized pipelines and with the existing sensitive-media blur gate applied before any decode begins. The focused cell should instantiate at most one `GtkVideo` or `GtkMediaFile` at a time per viewport, muted and looping, started only when the row is at least half visible and no sibling pipeline is active, and torn down through pause, file release, and poster restoration on unmap, on scroll-away, or on focus theft, because `GtkVideo` already exposes the `autoplay` and `loop` policy hooks while GTK itself provides no IntersectionObserver and Babble must supply the visibility computation from layout bounds and scroll-container signals ([Source](https://docs.gtk.org/gtk4/class.Video.html)). Detail view should graduate to `GtkVideo` with `GtkMediaControls` for unmuted explicit playback, keyboard shortcuts for play, seek, mute, and fullscreen, and an `AdwCarousel` only for the image case, since a single video never needs a carousel and a `GstStreamCollection` selection event will later serve any genuine multi-track clip ([Source](https://docs.gtk.org/gtk4/class.Video.html)) ([Source](https://gstreamer.freedesktop.org/documentation/playback/playbin3.html)). Thumbnail extraction should stay server-side through `preview_url`; client rasterization through video frames should be a fallback for missing posters, never the default per-row cost, and GIFV should follow the viewer’s existing rule of muted loop gated by power and autoplay preferences.

The implementation roadmap can be staged without breaking the current beauty of the suite, and the table below maps each phase to exact modules so the 800-line discipline, weak-signal rules, and install lists shape the work from day one. Phase one adds a new `mediainline.py` module owning policy, visibility gating, and the one-active-pipeline coordinator, refactors `mediaplayback.py` to expose progressive URI handoff beside the existing full-download path, and extends `mediabox.py` and `statusrow.py` with lazy cell construction, `mediacache.py` with poster reservation, `entities.py` with inline-playability helpers, runtime probing, and `data/io.github.mauriciobc.Babble.gschema.xml` with autoplay and data-saver keys, all registered in `src/meson.build` so the file-size rule passes. Phase two expands detail view through upgraded `mediaviewer.py` chrome, notification and Catch-Up parity in `notificationrow.py` and `catchup/tiles_render.py`, and the Flatpak manifest amendment for the codec extension. The weak-signal discipline matters throughout: every per-row observer must use `pages.connect_weak` or `pages.weak_method` rather than plain `connect`, because a C-level cycle keeps rows alive exactly as the timeline-memory test would expose (`src/statusrow.py`, `src/pages.py`, `src/test-timeline-memory.py`).

| Phase | Deliverable | Primary files and checks |
|---|---|---|
| Progressive timeline MVP | Visibility-gated muted looping inline playback with poster fallback and one-pipeline cap | New `mediainline.py`; changes to `mediabox.py`, `statusrow.py`, `mediaplayback.py`, `mediacache.py`, `entities.py`, `meson.build`, and GSettings schema |
| Detail player hardening | Seek, fullscreen, keyboard, audio-focus, and error reporting parity with the viewer | Changes to `mediaviewer.py` and `mediazoom.py`; `gtk4paintablesink` probe and `playbin3` selection behind a capability gate |
| Distribution and surfaces | H.264 reliability in Flatpak, notification and Catch-Up parity, and performance budgeting | Manifest extension entry in `build-aux/flatpak/io.github.mauriciobc.Babble.json`; `notificationrow.py`; `catchup/tiles_render.py`; `timelinebase.py` caps |

Testing must respect the harness as written: the suite runs under headless mutter with a 1280x1024 virtual monitor, pinned `LANG=C`, `LC_ALL=C`, and `GSK_RENDERER=cairo`, standalone `src/test-*.py` scripts that print `ok` or `FAIL` lines, and a strict Cairo fallback because a GL renderer without context aborts the process, which is already documented in the viewer-teardown failure mode (`AGENTS.md`, `src/meson.build`). New tests should therefore mirror `test-mediaviewer-teardown.py` by embedding a base-plugin Theora clip for network-free decode verification, looping open and close cycles to prove disposal order, and asserting geometry under mutter rather than Xvfb, while media-helper tests mirror `test-mediaviewer.py`, `test-mediabox.py`, `test-imagecache.py`, `test-imagedecode.py`, and `test-media-limits.py` for translation, keyboard, coalescing, and size-limit behaviour. The geometry-sensitive pair `compose widgets` and `timeline memory` should be extended to assert that inline video preserves row geometry at 1280x1024, and every new module must appear in both `src/meson.build` install lists and the standalone test registration or the file-size rule fails (`src/test-timeline-memory.py`, `src/test-file-size.py`). Manual verification competes alongside automation: `gst-inspect-1.0` probing in the Flatpak sandbox, metered-connection throttling, power-saver blocking, CW blur gating, single-pipeline eviction under fast scrolling, and first-load trace measurement reusing the project’s mutter-headless path.

## What remains uncertain before the first line ships

Three unknowns dominate the risk register and each admits a cheap experiment before commitment. The exact GNOME 51 runtime plugin set was inferred rather than enumerated from the manifest, so the first engineering move is a runtime inventory rather than a code change, and the absence of `bad` or `openh264` assumptions should be verified by attempting a real H.264 clip inside the sandbox before any timeline rollout date is promised. HTTP range support on Mastodon media hosts was also unverified from documentation, even though object-storage defaults and GStreamer’s `souphttpsrc` range seeking make progressive playback overwhelmingly likely, and a `curl -I` against a live remote URL will settle whether seeking is reliable or whether Babble needs a download-and-play fallback for non-compliant hosts ([Source](https://gstreamer.freedesktop.org/features/)). No benchmark establishes `GtkVideo` instantiation cost in PyGObject on Wayland, no GNOME-wide reduced-motion mapping to autoplay was verified, and Clapper reuse in production Python apps lacks confirmation, which together argue for starting with `GtkVideo` plus explicit visibility gating rather than a vendored player library ([Source](https://docs.gtk.org/gtk4/class.Video.html)) ([Source](https://github.com/Rafostar/clapper)). Signed or expiring media URLs, sidecar subtitles, Tor instances, and per-client implementation matrices for Tusky, Mammoth, and Elk remain undocumented in the evidence base and should not block the progressive MVP, because `url` null plus `preview_url` present already covers the own-upload transcoding state and single-track Mastodon clips make subtitle selection rare ([Source](https://docs.joinmastodon.org/entities/MediaAttachment/)).

## Conclusion

The report changes the framing from “add streaming” to “add visibility-gated progressive playback behind a codec-aware build”, because that narrower reading follows directly from Mastodon’s file model and from the Flatpak extension landscape. The novel implication is that Babble’s roadmap should sequence codec inventory and range verification before any widget work, since both determine whether progressive playback is even available to test; the widget itself is proven by the viewer’s existing pipeline and by `GtkVideo`’s preview scope. Treating adaptive demuxers, custom sinks, and Clapper as later insurance rather than first milestones keeps the project inside its memory, file-size, and teardown constraints while leaving the door open to browsers-grade detail playback without paying for it on every timeline row.
