# Prior video plan fails adversarial review

The prior streaming-video plan does not survive adversarial review in its original shape: its Flatpak codec story is inverted, its GVFS premise is untested, and its range-seeking, playbin3 readiness, and size assumptions are contradicted by direct runtime inspection and by Babble's own code, so the two-tier build must be re-sequenced behind six cheap experiments that collapse the roadmap from “build mediainline.py” to “stop downloading in the viewer first” if the URI path works. Tuba proves the field consensus is viewer-only playback with a Clapper-preferred, GtkVideo-fallback architecture, which validates keeping Babble's GtkVideo-first instinct while invalidating the plan to buy playbin3 track-selection for single-track Mastodon MP4s. The surviving core is narrow but real — progressive MP4 via GtkVideo/GtkMediaFile, metered and power gating, and pinned teardown discipline — and everything else (adaptive insurance, codec-extension naming, one-pipeline-per-viewport coordinator) is either unfunded by evidence or blocked by file-size, geometry, and Cairo-harness constraints. What follows replaces the prior roadmap with a kill-criteria-first sequence: inventory before widgets, viewer progressive before timeline inline, and playbin3 gated behind a falsifiable trigger that is currently false.

## Five load-bearing claims collapse under direct inspection

The prior report's spine — H.264 depends on codecs-extra, souphttpsrc range seeking is reliable, GtkMediaFile over GVFS is impossible so download-then-play is proven, playbin3 plus gtk4paintablesink is ready in PyGObject, and Mastodon enforces 99 MB at 1300 kbps — is wrong or unproven on every leg, and the falsification is mechanical rather than rhetorical. Installed GNOME 51 runtime inspection shows **H.264 decode does not live in codecs-extra; it ships in the base runtime via libgstlibav, while codecs-extra contains a single encoder file, libgstx264.so**, with avdec_h264 resolving to /usr/lib/x86_64-linux-gnu/gstreamer-1.0/libgstlibav.so and gtk4paintablesink, playbin3, souphttpsrc, and hlsdemux2 all resolving inside the base runtime — [Local runtime inspection, org.gnome.Platform//51 metadata + gst-inspect-1.0 inside flatpak run] — so both the prior report's claim that “H.264 MP4 remains the common case that depends on the extra branch” and its “automatic H.264 support unless the user opted out” framing misattribute the decoder, and the real silent failure is not a masked extension but a server that does not do Range or that redirects. The same inspection returns **vaapih264dec = NO and vulkanav1dec = NO inside the GNOME 51 runtime, with no libgstvulkan or libgstvaapi exposed**, so the plan's “explicit pipeline choice / prefer VA-API or Vulkan” framing treats a missing-driver problem as a solved choice, and its supporting citation is a single Arch forum post that the report itself labels “practitioner evidence rather than a guaranteed GTK backend default” — [Arch forum report](https://bbs.archlinux.org/viewtopic.php?id=244031&p=12). Range seeking, the entire feature for a 99 MB H.264 file over a redirecting CDN, was never probed: souphttpsrc “adds range request headers regardless of whether the server supports range requests or not” and “aborts during playback” — [Bug 722185](https://bugzilla.gnome.org/show_bug.cgi?id=722185) — and the element docs state “If the server sends redirects, the request fails instead of following the redirect” — [souphttpsrc docs](https://gstreamer.freedesktop.org/documentation/soup/souphttpsrc.html) — yet no curl -I, no Accept-Ranges evidence, and no redirect check against files.mastodon.social or any S3-backed media host appears in the report or the notes, and the counter is only that “object-storage defaults make progressive playback overwhelmingly likely.” The GVFS premise is a comment in Babble's own code, not a verified platform fact: src/mediaplayback.py:284-288 says “Gtk.MediaFile reads remote files through gvfs, whose http backend is unavailable inside a Flatpak sandbox,” and src/mediaplayback.py:320 only ever calls Gtk.MediaFile.new_for_file on a local temp file, while no code path tries Gtk.MediaFile.new_for_uri over an https:// URI which routes through souphttpsrc and uridecodebin rather than GVFS HTTP — and Tuba proves that alternative is live in production via its GtkVideo fallback calling video.set_file(File.new_for_uri(url)) directly for stream=true callers. The size ceiling is equally soft: Babble already reads per-instance limits from configuration.media_attachments (src/test-media-limits.py:67-76, src/mastodon.py media_size_limits()), older instances still advertise 40 MB, and mastodon.social showed “~68 MB observed despite 99 MB API value” — [Discussion #26709](https://github.com/mastodon/mastodon/discussions/26709) — while the viewer download path has **no size cap at all**, imagecache capping at MAX_IMAGE_RESPONSE_BYTES = 16 * 1024 * 1024 (src/imagecache.py:71) but mediaplayback.download() / _Download (src/mediaplayback.py:51-176) streaming 64 KiB chunks to a temp file unbounded.

What survives is smaller and more honest. Mastodon serves progressive files rather than adaptive playlists, and that claim holds: video and gifv travel through MediaAttachment url as progressive files with preview_url posters and meta carrying duration, fps, size, dimensions, audio encoding and bitrate — [MediaAttachment](https://docs.joinmastodon.org/entities/MediaAttachment/) — **Mastodon serves progressive files, never adaptive playlists**, and the WebSocket streaming API is a separate timeline push channel, so “streaming video” for Babble genuinely means incremental play from a remote HTTP range source rather than a manifest ladder. HLS absence also holds — no hls, m3u8, dash, or adaptive string exists in src/ — but that hold undermines the plan's own “adaptive insurance” justification for playbin3, because Babble's data model has no federated HLS embed for insurance to cover. playbin3 readiness does not survive: Babble contains **zero Gst. usage anywhere (grep -rn “Gst.” src/*.py returns nothing)**, with no Gst.init(), no Gst.parse_launch, no bus handling, and no introspection test, and gtk4paintablesink is a Rust plugin (gst-plugin-gtk4, MPL, from gst-plugins-rs) whose DMABuf path requires GTK ≥ 4.14 with the dmabuf cargo feature enabled — [gtk4paintablesink](https://gstreamer.freedesktop.org/documentation/gtk4/index.html) — so “readiness in PyGObject” is asserted from docs, never demonstrated from Python. Track selection, the other playbin3 justification via GstStreamCollection — [playbin3 docs](https://gstreamer.freedesktop.org/documentation/playback/playbin3.html) — has no source data in Mastodon attachments: single-track H.264 MP4 with AAC audio, one video per post, no sidecar subtitles, a posture Tuba mirrors by shipping no subtitle or track-selection UI at all. The file-size and teardown constraints finish the falsification: src/statusrow.py at 793 lines, src/notificationrow.py at 797, and src/catchup/tiles_render.py at 785 sit 7, 3, and 15 lines under the 800-line limit that src/test-file-size.py:35 enforces (LIMIT = 800, failing any module over the limit “in neither SEAMS nor EXCEPTIONS” at src/test-file-size.py:138-142), with mediaviewer.py at 1058 lines already a declared exception (src/test-file-size.py:72-76), so Phases 1 and 2 adding code to statusrow.py, notificationrow.py, and tiles_render.py are unimplementable without first splitting those files or declaring new exceptions — and a coordinator that plain-connects rows to a process-wide singleton recreates the exact C-level cycle that test-timeline-memory.py exists to catch, against CLAUDE.md's requirement that pages.connect_weak or pages.weak_method preserve the lifetime discipline sysstate.py:16-17 already warns about. The Theora-only teardown pattern compounds the test trap: src/test-mediaviewer-teardown.py:86-88 deliberately avoids H.264 because “an H.264 clip also needs a decoder that GTK does not [ship],” so a timeline test with a real H.264 clip cannot run in CI without the codec the plan is still probing for, and GSK_RENDERER=cairo pinned in src/meson.build means the DMABuf and GL paths the plan celebrates will be exercised by no test in the suite.

## Tuba ships Clapper polish over a download fallback

Tuba's codebase answers the competitive question directly: **Tuba has no inline timeline playback at any level**, with all playback living in a single full-window Views.MediaViewer (carousel plus morph reveal) backed by Clapper preferred and GtkVideo fallback for video and GIFV and a hand-rolled GStreamer uridecodebin pipeline for audio, and no subtitles, track-selection UI, HLS or multi-bitrate code of its own, duration badges, or data-saver anywhere. Timeline attachment is Widgets.Attachment.Image feeding FocusPicture via Helper.Image.request_paintable(entity.preview_url, entity.blurhash), with a play-icon overlay for video and GIFV and on_click routing to on_any_attachment_click(entity.url) which opens MediaViewer — and no GtkVideo or ClapperGtk.Video is instantiated in any timeline or attachment widget, every Video construction sitting inside MediaViewer.add_media. The viewer itself is a dual-backend compromise whose cost is visible in every method written twice behind compile-time #if CLAPPER: the Clapper path builds ClapperGtk.Video with auto_inhibit true, Clapper.MediaItem.cached caching, download_dir at clapper cache with download_enabled true and LRU cleanup keeping 10 files, ClapperGtk.SimpleControls fading overlay, MPRIS feature (org.mpris.MediaPlayer2.Tuba.instance<N> handling both CLAPPER_0_10 enhancer-proxy and older CLAPPER_MPRIS APIs), and queue.progression_mode REPEAT_ITEM for GIFV, while the fallback GtkVideo path sets graphics_offload ENABLED and loop true for GIFV and **fully downloads non-stream video first (download_video → Utils.Host.download(url) → video.set_filename(path)), streaming only File.new_for_uri(url) when stream=true — a flag passed solely for audio (remote-audio fallback, Funkwhale, Drive) and PeerTube preview-card video (src/API/Status/PreviewCard.vala:245), never for Mastodon video attachments from the timeline**. Audio is the exception that proves the rule: Widgets.Audio.Player plus Stream.vala runs a raw GStreamer string pipeline “uridecodebin ! audioconvert ! audio/x-raw,channels=2 ! volume ! level interval=100000000 ! autoaudiosink” via Gst.parse_launch with bus handling for ERROR, EOS, STATE_CHANGED, ELEMENT(level), ASYNC_DONE, and DURATION_CHANGED, a 1s position poll, and seek_simple(FLUSH|KEY_UNIT) scrubbing — the only genuinely streamed path, and the weakest code in the stack, with string-launch fragility and 1s polling that Babble should not copy. The attachment model confirms Babble's parity checklist: Attachment.vala parses only meta focus, **no duration, width, height, or frame-rate fields are read at all**, preview_url falls back to url when null or empty, timeline tiles always render preview_url stills even for video, GIFV, and audio with no animated GIFV preview, no waveform, and no duration badge, and the UNKNOWN remote-fallback consent dialog (“Your instance hasn't proxied or can't handle this attachment…”) is Tuba's distinctive UX steal, guessing MediaType from filename content-type and opening externally when unknown.

Packaging and policy expose the remaining gaps. Tuba's codec story is Flatpak extension-based: build-aux/dev.geopjr.Tuba.Devel.json declares runtime org.gnome.Platform 50 with add-extensions org.freedesktop.Platform.ffmpeg-full v24.08 and com.github.rafostar.Clapper.Enhancers v stable, builds Clapper 0.10.0 from git with -Dintrospection=enabled -Dvapi=enabled -Ddiscoverer=disabled -Dmpris=disabled and -Dclapper=enabled -Dgstreamer=enabled in Tuba's config, while meson treats clapper and gstreamer as plain feature (auto) options emitting CLAPPER, CLAPPER_0_10, and CLAPPER_MPRIS defines — a correct architecture for Babble to copy in shape (single binary, capability-detected backends) but wrong to copy in content, because Clapper is pre-1.0, absent from org.gnome.Platform, and its own readme warns the libraries should be considered unstable until version 1.0 — [Clapper GitHub](https://github.com/Rafostar/clapper). Policy is where Tuba is strictly behind: **no metered, no power-saver, and no autoplay-policy code at all** (grep across src/ returns nothing; only auto_inhibit true on ClapperGtk.Video and media_viewer_last_used_volume), GIFV always looping and on_carousel_page_changed calling play_video(pos) immediately, while Babble defers any video, audio, and GIFV download behind preview plus Load button on metered connections, blocks GIFV autoplay on power-saver via gtk-enable-animations plus power-saver gate, and inhibits idle only for video and audio while playing. Error UX follows the same split: Tuba's non-Clapper download failure is catch (Error e) { app.inform(_("Error"), e.message) } with GStreamer errors only logged as critical(@"Gst Error: …"), no codec-missing guidance found, while Babble surfaces a translated Could Not Load Media StatusPage with Try Again and Open in Browser on stream.notify::error. Teardown safety inverts the hierarchy: Tuba's ~Item destructor for Gtk.Video calls media_stream.stream_unprepared(); set_file(null); set_media_stream(null) while the widget is being torn down, against Babble's pinned rule (pause, drop widget, let disposal retire the GstPlay thread; never clear stream early, SIGSEGV in g_type_check_instance_is_fundamentally_a) pinned by 12 open-close cycles in test-mediaviewer-teardown.py. Tests settle the maturity verdict: Tuba's tests/ contains exactly 11 files (Blurhash, Celebrate, Counting, DateTime, Html, TagExtractor, Tracking, Units, WebApHandler, ShareHandler) and **grep for media, video, audio, or attach returns no media tests**, with Blurhash testing decoder math rather than rendering, while Babble runs roughly 50 standalone src/test-*.py scripts under headless mutter at 1280×1024 with GSK_RENDERER=cairo and LANG=C, including mediaviewer teardown with an embedded base64 Theora clip — so the market leader deliberately has not solved inline timeline playback either, Babble's viewer-first instinct is the field's unstated consensus, and Tuba's download-then-play model validates that even with Clapper available, cold remote streaming without a cache is unreliable enough that Tuba pre-downloads, meaning Babble's progressive-range plan is riskier than Tuba's, not safer, until Phase 0 proves Range works.

## Experiments precede widgets or the roadmap collapses

Six cheap experiments, none requiring product code, decide whether the two-tier plan survives, and the ordering is the finding: the prior report lists the unknowns but sequences widget work first. Experiment 1 runs Gtk.MediaFile.new_for_uri inside the Flatpak sandbox against https://files.mastodon.social/…mp4 via Gtk.MediaFile.new_for_uri, Gtk.Video.new_for_uri, and Gio.File.new_for_uri plus new_for_file, recording which path plays and whether errors are GVFS-related or codec-related; if URI playback works, Phase 1 collapses from “progressive URI handoff beside download” to “delete the download,” a smaller higher-value change. Experiment 2 runs curl -I and curl -r 0-1023 against live url values from mastodon.social and at least one small-instance S3 host, recording Accept-Ranges, Content-Range, 206 versus 200, and Location redirects, then plays the same URL through souphttpsrc and playbin3 in the sandbox and seeks to 50%; if the host returns 200 to a Range request or redirects, souphttpsrc will fail per Bug 722185 and the fallback is download-then-play or a proxy, not inline streaming. Experiment 3 inventories the GNOME 51 runtime plugin set on a clean machine without pre-installed codecs-extra, running the gst-inspect-1.0 matrix (avdec_h264, vaapih264dec, souphttpsrc, playbin3, hlsdemux2, gtk4paintablesink, vulkanav1dec) and listing the codecs-extra plugin directory; this critique found libgstlibav (decode) in base and only libgstx264 (encoder) in extra with VA-API and Vulkan absent, so a clean confirmation deletes the manifest amendment from the roadmap and records hardware decode as unavailable, changing the performance story entirely. Experiment 4 spikes gtk4paintablesink in PyGObject under Cairo and under GL (Gst.init(), playbin3 to gtk4paintablesink, get_paintable() embedded in Gtk.Picture, playing the Theora clip and a real H.264 clip), recording whether the paintable renders, whether bus errors surface as Python exceptions or criticals fatal under G_DEBUG=fatal-criticals, and who owns the pipeline thread on widget disposal; if Cairo cannot render the sink, the test suite cannot cover Phase 2 and the playbin3 tier must be manual-test-only, a strong argument for staying on GtkVideo. Experiment 5 measures per-pipeline cost on Wayland under headless mutter at 1280×1024 by instantiating 1, 2, and 4 GtkVideo pipelines playing a 1300 kbps clip and measuring RSS and CPU via bench/timeline_bench.py (main_ms, stall_max_ms); if one pipeline costs more than the retained-RSS budget allows on fast scroll create and destroy churn, the timeline tier is infeasible without a shared pipeline that GtkVideo does not support, and the plan must be re-scoped to GIFV-only animation. Experiment 6 dry-runs file-size and registry impact by sketching mediainline.py (coordinator plus visibility plus policy plus errors plus probe) against src/test-file-size.py limits, naming which files grow, by how much, which split is needed before inline video can land, and whether the new module needs po/POTFILES.in plus module boundary review; if statusrow.py, notificationrow.py, and tiles_render.py must split first, that split is Phase 0 and should be costed as such. Experiments 1 and 2 are kill criteria: if URI playback works and Range works, the hardest problems shrink to “use the URI path”; if either fails, inline streaming is not shippable and the correct recommendation is improve the viewer (cache, cap, progress) plus GIFV timeline animation plus duration badges, the single highest-leverage slice Tuba's benchmark already identifies.

The revised roadmap reorders to codec inventory, viewer progressive, timeline inline, PeerTube bridge, and detail hardening, cutting playbin3 and custom sinks until viewer and HLS both demand them while stealing Tuba's stream=true progressive delivery and remote-url dialog and avoiding its download-everything default and #if CLAPPER matrix. Phase 0 is the codec and range inventory with no widget code: a runtime gst-inspect-1.0 probe script, curl range checks against live mastodon.social media hosts, a new_for_uri sandbox spike, and the file-size dry run, with the manifest add-extensions amendment for org.freedesktop.Platform.ffmpeg-full only if the clean-install probe proves decode is absent — and if new_for_uri works, Phase 0 ends with the download path deleted rather than complemented. Phase 1 replaces full-download in _download_stream with Gtk.MediaFile.new_for_uri(url) progressive play plus download-as-fallback only on notify::error, keeps the metered deferral and teardown rule, and surfaces a translated codec-missing error only if the probe proves a decoder absent, **never naming codecs-extra as the missing extension** because the encoder is the maskable piece and decode is in base — the error must name the actually missing decoder or ffmpeg-full, which is what Tuba's silent black-screen and inform(Error) fail to do. Phase 2 narrows timeline inline to GtkVideo muted-loop in the MediaBox tile only when at least 50% visible, maximum one active pipeline app-wide, unknown to pause, reusing the _TextureCache poster until prepared, with GIFV respecting power-saver and video never autoplaying with sound, and with duration badges drawn from server meta and preview_url posters rather than GstDiscoverer probing, because the plan's discovery fallthrough doubles test surface for metadata the server already supplies — **duration badges and posters are server-supplied, so GstDiscoverer is unnecessary default work**. Phase 3 opens notifications and Catch-Up to the viewer (not inline) rather than inventing click handling those surfaces lack — notificationrow.py renders static 96px thumbnails with no click-to-viewer (src/notificationrow.py:296-320) and Catch-Up tiles show a play icon but click opens thread not playback (src/catchup/tiles_render.py:410-434), so parity requires inventing the click, keyboard, and sensitive gating those surfaces lack — plus Tuba's remote-url recovery dialog and a PeerTube card browser bridge rather than enhancer rewrites. Phase 4 defers detail hardening behind a falsifiable trigger: a Mastodon attachment with two selectable streams exists, which is currently false, so playbin3 plus gtk4paintablesink (and the MPRIS stretch via 200 lines of Gio D-Bus) stay out until that trigger fires, and Clapper vendoring stays out permanently given pre-1.0 API churn and absence from org.gnome.Platform. The cut and defer list is explicit: cut playbin3 track selection, GstDiscoverer probing, adaptive insurance, Clapper enhancers, and unified Soup.Cache; defer custom sinks, MPRIS, audio visualizer (the only Tuba capability requiring a bespoke Gst pipeline via level element, which has no Mastodon-API driver), and spatial carousel matching to Phase 4.

Tests must prove each phase inside Babble's pinned harness rather than copying Tuba's nonexistent media tests. test-media-progressive.py mirrors test-mediaviewer-teardown.py by serving an embedded Theora clip via a loopback HTTP Range server and asserting Gtk.MediaFile.new_for_uri(loopback) reaches prepared, plays within 5 s, seeks with timestamp advance, and leaves notify::error null, with fallback download triggered on 200-non-range or error — stealing Tuba's stream=true pattern while exceeding it by proving range telemetry rather than merely “plays.” test-media-inline-gate.py mirrors test-mediabox.py at 1280×1024 by asserting tiles start paused with poster, on visible ≥50% play muted, on scroll-away pause plus poster restore, metered GSettings creating no MediaFile, power-saver blocking GIFV autoplay, and a CW or blur tile never constructing a pipeline via a MediaFile.new spy — exceeding Tuba by pinning the gate Tuba lacks. test-media-inline-teardown.py extends test-mediaviewer-teardown.py with 12 open and close cycles of the timeline cell under mutter (not Xvfb) asserting the same five invariants (widget disposed, stream not freed early, file intact, child removed, not playing) plus weakref rows freed mirroring test-timeline-memory.py, avoiding Tuba's stream_unprepared plus set_media_stream(null) mid-teardown pattern. test-media-codec-probe.py probes avdec_h264, vaapih264dec, souphttpsrc, playbin3, gtk4paintablesink, and hlsdemux2 via Gst.Registry and, when the H.264 decoder is absent, asserts the translated error names the actually missing extension rather than the encoder. test-media-timeline-geometry.py extends test-timeline-memory.py by asserting row allocated height unchanged within ±2 px versus poster-only at 1280×1024 with inline cell, recycled row rebind not leaking, and TIMELINE_MAX_ITEMS=400 still enforced — Babble-only risk because inline changes row height budget and GtkVideo intrinsic size under Cairo paints nothing while still measuring. Every new module must land in src/meson.build install_data and, if it translates strings, in po/POTFILES.in, or the file size rule fails.

## Unpriced risks will ship as silent failures

Nine failure modes remain first-order until priced, and several ship as silent black pictures, background audio, or leaked pipelines. Multiple pipelines blow the RSS budget because each Gtk.MediaFile or GtkVideo owns a GstPlay pipeline with its own thread and decoder buffers — the teardown test exists because “the pipeline owns a signal-adapter thread” (src/test-mediaviewer-teardown.py:5-10) — yet the plan caps pipeline count without capping decoder DMABuf or system-memory allocation, stating no texture-plus-pipeline combined budget and addressing no fast-scroll create and destroy churn against the 96 MB retained-RSS envelope. Wayland DMABuf and VA-API bugs are untestable in Babble's harness by construction: tests pin GSK_RENDERER=cairo because “letting GSK pick a GL renderer makes the suite depend on a working GL context… libepoxy then aborts the process” (src/meson.build:190-199), the DMABuf path requires the dmabuf feature with GTK ≥ 4.14, and VA-API and Vulkan decoders are absent in the GNOME 51 runtime, so under Cairo the sink falls back to system memory while under a real GPU it does not, and the plan's GPU-composited promise will be exercised by no test. Flatpak masking threatens the driver rather than the codec: org.freedesktop.Platform.GL.default and VAAPI extensions are enable-if active-gl-driver and download-if active-gl-driver, so hardware decode vanishes on hosts whose drivers do not match regardless of codecs-extra, --device=dri in build-aux/flatpak/io.github.mauriciobc.Babble.json:15 notwithstanding, and blaming the wrong extension in a translated error is worse than a generic error. Live metered and power transitions are checked once, at viewer construction, and never while playing: MediaPlayback._show_stream checks _system_state('metered') once (src/mediaplayback.py:242-246), GIFV autoplay checks gtk-enable-animations and power-saver once (src/mediaplayback.py:341-342), sysstate.monitor() emits notify::metered and notify::power-saver on change (src/sysstate.py:92-100) but no media code subscribes — StreamingManager already subscribes to notify::online (src/streaming.py:196-198) — so a timeline that starts on Wi-Fi and moves to metered mid-scroll keeps decoding with no equivalent media subscription. Sensitive-media re-gating is a grid-build check rather than a playback check: MediaBox.set_media applies the show-sensitive-media gate and blurred revealer at build time (src/mediabox.py:460-487), BlurredPicture blurs at snapshot (src/mediabox.py:412-424), and each of statusrow.py, catchup/rows.py, and catchup/tiles_render.py re-reads show-spoilers and show-sensitive-media, so inline autoplay instantiating a pipeline on visibility must re-check media_revealed on every reveal and hide toggle and on row recycle (ui dict persists across recycling, src/mediabox.py:449-452), and a pipeline started while revealed keeps playing after the user hides the media. Reduced-motion is gated for GIFV in the viewer but not for timeline video in the plan: the viewer checks Gtk.Settings.get_default().get_property('gtk-enable-animations') for GIFV (src/mediaplayback.py:341-342) and src/style.css honors it for CSS animations, yet the timeline tier autoplays muted looping video on visibility with no gtk-enable-animations gate, only noting that no GNOME-wide reduced-motion mapping to autoplay was verified — against Mastodon's own preference defaulting autoplay GIFs off for accessibility and Section508 guidance warning that autoplaying content “can interfere with assistive technologies” — [Section508 blog](https://www.section508.gov/blog/avoid-auto-playing-content/) — shipping video autoplay where GIFV autoplay is gated registers as a regression. Signed and expiring URLs break streaming differently than downloading: mediaviewer.show_index trusts attachment.get('url') or attachment.get('remote_url') with “no re-fetch, no signature, no expiry check” (src/mediaviewer.py:606), a downloaded file is immune to expiry after fetch while a streamed URI is not, mid-play 403 has no recovery path (no refresh via GET /api/v1/media/:id, no fallback to download), and whether Mastodon media hosts issue signed URLs at all is undocumented (“I found no reliable source confirming signed media URLs”), so the failure mode is unscoped rather than absent while url null plus preview_url present (own-upload transcoding, src/api/media.py polling) forces the tile to distinguish “no URL yet” from “no video.” App lifecycle gaps complete the register: the viewer inhibits idle only for video and audio, never for muted looping GIFV (“A muted, looping GIFV is no reason to keep the screen on,” src/mediaplayback.py:417-420), the timeline explicitly never survives minimization or sleep as a background track yet provides no mechanism — no fullscreened handler, no application shutdown pause, no sysstate notify::online pause, no audio-session handling — and paused GstPlay pipelines keep their adapter threads alive, so suspend with a live pipeline is the default outcome. Audio focus and MPRIS are dismissed with anecdotes rather than a Flatpak permission analysis: the report cites Celluloid and Totem MPRIS bugs and declares MPRIS out of scope, Babble's manifest has no --own-name=org.mpris.MediaPlayer2.* (contrast Tuba), and muted-by-construction timeline video still decodes audio tracks it never plays.

Open questions to resolve before committing beyond Phase 0 stay narrow and answerable. The GNOME 51 runtime plugin set must be re-enumerated on a clean machine because this host already has codecs-extra installed system-wide, which may mask a missing-default case. No cursor exists on whether gtk4paintablesink under GSK_RENDERER=cairo works at all via its system-memory path versus requiring GL, and the suite cannot test the GL path by construction. Per-pipeline RSS and CPU in PyGObject on Wayland are unmeasured, the one-pipeline cap is unvalidated against the 96 MB retained budget, and no estimate exists of whether mediainline.py fits under 800 lines with coordinator, visibility, policy, errors, and probing without the second module the roadmap does not name. Tuba's Flathub-stable manifest was unavailable (only the Devel manifest was in-repo), so stable ffmpeg-full and Enhancers parity is marked inferred and the verifier should check the Flathub repo before quoting codec numbers. Whether the H.264 test clip's absence from CI is permanent or a codec-probe artifact determines whether progressive range telemetry can ever be automated inside Babble's harness, and the loopback Range-serving fixture design (Python http.server with Range support inside the test, 60 s meson timeout) remains unvalidated. Each of those questions maps to a Phase 0 experiment rather than a quarter of design.

## Conclusion

The adversarial review changes the question from “how do we build two-tier streaming” to “which single URI experiment deletes half the roadmap,” because the codec inversion, the untested GVFS premise, and the uncapped download together mean the prior plan engineers a coordinator for a problem it never proved exists. Tuba's contribution is then clarifying rather than aspirational: a viewer-only, Clapper-first architecture with zero inline playback, zero metered discipline, and zero media tests sets a bar Babble already clears on discipline and clears nowhere on playback, so beating it requires only honest progressive playback behind consent gates, not a second player backend. The revised sequence therefore earns inline timeline work by first proving range, URI, and cost inside the sandbox and the harness, and until those proofs land, the shippable gain is capping, caching, and badging the viewer Babble already has.
